# 模型映射

在「站点管理 → 模型映射」创建规则，为客户端请求的模型指定实际回答模型。每个账号独立保存，只能选择当前账号自己的渠道，接入地址不变。保存立即影响新请求，已在执行的请求继续使用原规则；重启后保留。

例如，请求模型填 `gpt-6-sol`，目标选择 **OpenCode Go / deepseek-v4.1-flash**。启用后，客户端继续发送 `gpt-6-sol`，网关实际调用 `deepseek-v4.1-flash`。响应保留真实模型身份，请求日志显示两个名称，用量和健康评分归到实际调用模型。

## 匹配与调度

- 模型名称精确匹配，不支持通配符，也不会递归匹配其他映射。
- 来源选「所有来源」或指定 IPv4 / IPv6；指定 IP 优先。同一模型不能启用两条覆盖同一 IP 的规则，也不能启用两条全体规则。
- IP 取 TCP 连接来源，不信任 `X-Forwarded-For`。先经过当前账号白名单，映射不会赋予访问权限。
- 每条可选 1–16 个渠道，每个渠道指定一个实际模型。按现有评分、优先级和权重调度，顺序不代表优先级。
- 命中后仅在所选渠道间重试；停用、额度保护、限流、熔断和并发限制继续生效。全部不可用时返回错误，不转向其他渠道。
- `/v1/models` 会展示当前来源可使用的映射名称；原渠道模型目录仍然保留。配置本身不会触发生成或探测。

## 协议范围

支持 `/v1/responses` 与 `/v1/chat/completions`。目标支持原协议时只替换模型，保留完整请求。OpenCode Go 优先使用其原生入口，继续保留客户端的会话 ID，不切换到余额计费。

当目标仅提供 Chat Completions 时，可将 Responses 的文本、标准 `function` 工具、多轮工具结果和流式事件转换。支持 `reasoning.effort` 转为 `reasoning_effort`，具体取值由目标模型决定。流中断会返回失败事件；Token 上报与工具调用 ID 保留。

转换不支持图片等多模态输入、内置工具、自定义工具、命名空间、服务端会话、加密推理项、结构化输出等 Responses 专用功能。无法转换时会在本地报错，或尝试规则内支持原协议的其他渠道。目标模型的能力不会因为映射而提升；Codex 等客户端所用工具是否支持，仍取决于上游。

## 保存与备份

规则保存在各账号目录的 `model-mappings.json`，随整个 `data/` 备份即可，不新增数据库或服务。最多 64 条规则。配置文件损坏时停止这两个入口的转发，重新保存规则后恢复，避免意外请求其他渠道。

验证采用隔离的模拟上游；另用 OpenCode Go 验证过 `gpt-6-sol → deepseek-v4.1-flash` 的 Chat、Responses 和流式 Responses。真实测试是手动发起，不会自动重复。
